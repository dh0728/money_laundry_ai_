# 시험 설계 - rule_engine

## 목적
서비스의 Alert 는 **모델이 거래를 고르고(탐지), 규칙 기반 알고리즘이 묶은(묶기)** 결과다.
Alert 생성기를 룰엔진에 귀속시키는 방향에서, 탐지와 묶기 각각이 무슨 일을 하는지와 씨앗을 모델이 고를 때와 룰이 고를 때의 차이를 정답 라벨로 잰다.
서비스 안의 비교는 사람 판정만 쓰므로(룰엔진 설계안 D6), 정답 라벨 기준 수치는 이 저장소에서 따로 낸다.

| 단계 | 누가 하나 |
|---|---|
| 탐지 (어떤 거래가 의심인가) | 이진분류 모델, 또는 룰 |
| 묶기 (어떤 거래들이 한 사건인가) | Alert 생성기 (`money_laundry` worker/alerts) |

## 실험 목록

| # | 비교 | 단위 | 보여주는 것 | 필요한 것 | 상태 |
|---|---|---|---|---|---|
| 1 | 모델 탐지 거래: 묶기 전 vs 묶은 뒤 | 거래 | 생성기가 무엇을 떨구고 무엇을 더하는지 | 이진 모델 점수, 생성기, 라벨 | 노트북 작성. 실제 데이터로는 아직 안 돌림 |
| 2 | 모델 점수 ≥ 기준 vs 룰 적중 거래 | 거래 | 탐지만 놓고 본 모델과 룰의 차이 | 룰 적중 거래 목록 | `03_rule_vs_model.ipynb` 작성. 룰은 조건 여러 개를 AND 로 묶는 구조(2026-11-23 변경). 룰 쪽은 HI-Small 로 끝까지 돌려 봄. 모델 쪽은 점수 파일을 넣고 돌려야 한다 |
| 3 | 모델 씨앗 Alert vs 룰 씨앗 Alert | Alert | 같은 묶기에서 씨앗 출처만 바꿨을 때의 차이 | 2의 룰 적중 거래를 생성기에 넣기 | 2 다음. 템플릿 하나(FAN-IN)부터 |

1번은 2·3번의 기준선이다. 2번은 3번을 하면 따라 나온다.

## 공통 설정
- **데이터**: HI-Large. 평가 구간은 이진분류 실험의 테스트 구간(2022-10-17 ~ 10-30). 처음에는 HI-Small(09-09 ~ 09-10)로 끝까지 한 번 돌린다
- **생성기**: 서비스 저장소(`../money_laundry`, dev)의 `alerts/block_graph.py`, `alerts/seed_promotion.py` 를 그대로 불러온다. 복사하지 않는다. 정책은 `BlockPolicy()` 기본값
- **생성기 입력**: 평가 구간과 그 앞 14일(블록 기간 상한 336시간)의 거래. 앞 14일은 구조를 볼 때만 쓰고 씨앗과 지표에는 넣지 않는다
- **금액**: 보낸 금액을 서비스의 고정 환율(`fx_rates_usd_v1`)로 USD 환산
- **모델 기준값**: 서비스 이진 모델 `multi_fraudgt_hgb` 의 spec 값. 의심 기준 0.194997844, 씨앗 보강 low 0.1 / floor 0.01. 다른 모델의 점수를 넣으면 그 모델 기준으로 바꾸고 보강은 끈다
- **라벨**: 세탁 중 Patterns 파일에 없는 것은 `NO_PATTERN`. 재현율은 세탁 전체 기준과 패턴 세탁 기준을 둘 다 낸다

- **코드**: `code/rule_engine/`. 공통 로직은 `gen_lib.py`, 노트북은 번호순
- **결과**: `code/rule_engine/results/<DATASET>/<실험명>/`
- **문서**: 이 폴더. 실험마다 결과가 나오면 `NN_report.md` 로 정리한다

## 실험 1 — 묶기 전 vs 묶은 뒤 (`01_before_after_grouping.ipynb`)

| 단계 | 고른 거래 | 서비스 코드 |
|---|---|---|
| ① 모델 씨앗 | 점수 ≥ 의심 기준 | `alert_pipeline.save_alerts` 의 씨앗 수집 |
| ② 씨앗 보강 | ① + 씨앗과 이어진 낮은 점수 거래 | `seed_promotion.promote` |
| ③ 묶은 뒤 | Alert 에 들어간 거래(씨앗 + 연결 거래) | `block_graph.build_block_graphs` |

내는 표
1. 세 단계의 고른 거래 수, 세탁, 정상, 정밀도, 재현율
2. Alert 에 못 들어간 씨앗: 탈락 사유 × 실제 라벨
3. 보강으로 들어온 거래와 연결 거래의 실제 라벨
4. 패턴별 재현율이 단계마다 어떻게 바뀌는지
5. Alert 단위: 개수, 크기, 세탁 비율, 구조 근거 종류

돌리기 전에 정할 것
- `SCORES`: 이진 모델 테스트 점수 parquet (edge_id, y, score). 발표용 수치는 서비스 모델의 점수여야 한다
- 서버의 `money_laundry` 는 dev 브랜치여야 한다

## 실험 2 — 모델 없이 패턴 룰만 vs 이진분류만 (`03_rule_vs_model.ipynb`)

묶기는 없다. 세탁 거래를 **고르는 일**만 두 방법으로 하고 거래 단위로 잰다.

| 방법 | 고르는 기준 |
|---|---|
| 룰만 | 패턴 6종을 룰로 적어 원장 전체에 건다. 룰에 걸린 근거 거래가 고른 거래다. 모델 점수는 쓰지 않는다 |
| 이진분류만 | 점수 ≥ 의심 기준(검증 구간에서 고른 값) |

**지표에서 빼는 세탁 (2026-11-23 결정)**: 무패턴 · STACK · BIPARTITE. 무패턴은 정상 거래와 특징이 비슷하고, STACK · BIPARTITE 는 생성된 데이터가 패턴의 실제 정의와 달라서다.
- 노트북 0절 `EXCLUDE` 로 정한다. **정답도 오답도 아닌 것으로 두고 뺀다**(이진분류 08 · 09 보고서에서 무패턴을 뺀 것과 같은 계산). 룰이나 모델이 이 거래를 골라도 고른 거래 수에 넣지 않고, 세탁 수와 재현율 분모에도 넣지 않는다
- 룰은 원장 전체를 그대로 본다. 이 거래들도 원장에 있는 거래라 상대 계좌 수를 셀 때는 들어간다
- HI-Small 에서 빠지는 세탁은 2,642건(보정 구간 2,143 + 평가 구간 499)이고, 남는 세탁은 6종 패턴 1,880건(보정 1,423 + 평가 457)이다

### 룰 정의 (`rule_lib.py`)
**룰 하나 = 조건 여러 개의 AND.** Oracle 시나리오가 집계값 여러 개를 임계값과 비교해 AND 로 묶는 것과 같은 구성이다.
처음에는 "세기 ≥ 조건값" 하나만 썼는데 정상 계좌가 너무 많이 걸려서(아래 결과 표) 바꿨다.

| 조건 | 뜻 | 후보 (노트북 0절) |
|---|---|---|
| ① 거래 필터 | 룰이 세는 거래를 먼저 거른다. 걸러진 거래는 세지도 않고 근거 거래도 안 된다 | `FILTERS` |
| ├ 건당 최소 금액 | USD 환산 금액이 이 값 이상인 거래만 | 0 / 1,000 / 5,000 |
| └ 처음 거래하는 상대만 | 그 (송금 계좌 → 수취 계좌) 쌍의 첫 거래만. 데이터 처음부터 본다 | 끔 / 켬 |
| ② 기간 | 트리거 시각을 포함해 직전 `W` 를 돌아본다 | 1일 / 3일 / 7일 |
| ③ 세기 ≥ 조건값 | 기간 안에서 센 패턴의 크기 | `GRID` |
| ④ 반복 없음 (FAN 만) | 기간 안 거래 수 = 상대 계좌 수. 모든 상대와 한 번씩만 거래 | 허용 / 없음 |

①의 필터 후보는 `없음`, `1천↑`, `첫거래`, `첫거래+1천↑`, `첫거래+5천↑` 다섯 가지다.
Oracle 공개 문서에서 확인한 것은 "시나리오 = 필터 + 집계값(금액 합계, 건수)을 임계값과 비교해 AND" 라는 구성까지다. 위 조건의 **종류와 값은 Oracle 에서 가져온 것이 아니라** HI-Small 을 보고 정했다.
`건당 최소 금액` 은 그 구성에서 필터 자리에 해당한다. `처음 거래하는 상대만` 과 `반복 없음` 은 데이터에서 나온 조건이다
(패턴 세탁 거래의 85 ~ 94% 가 그 쌍의 첫 거래, 정상 거래는 09-05 이후 날짜별로 3 ~ 9%).

③의 세기는 룰마다 다르다. 대상 계좌의 거래 하나하나가 트리거이고, 적중한 트리거의 기간 안에서 패턴을 이루는 거래가 근거 거래(= 룰이 고른 거래)다.

| 룰 | 대상 | 트리거 | 세기 | 근거 거래 | 금액 조건 |
|---|---|---|---|---|---|
| FAN-OUT | 송금 계좌 A | A 의 출금 | 기간 안 서로 다른 수취 계좌 수 | 기간 안 A 의 출금 전부 | ① 만 |
| FAN-IN | 수취 계좌 A | A 로 온 입금 | 기간 안 서로 다른 송금 계좌 수 | 기간 안 A 의 입금 전부 | ① 만 |
| GATHER-SCATTER | 가운데 계좌 H | H 의 출금 | min(기간 안 송금 계좌 수, 첫 입금 뒤 수취 계좌 수) | 기간 안 입금 + 첫 입금 뒤 출금 | ① 만 |
| SCATTER-GATHER | 도착 계좌 D | D 로 온 입금 | 같은 출발 계좌 S 에서 와서 D 에 닿은 경유 계좌 수. `S → 경유` 가 `경유 → D` 보다 먼저 | 그 경유 계좌들의 두 단계 거래 | ① 만 |
| CYCLE | 출발 계좌 A | 경로의 첫 거래 | 출발 계좌로 돌아온 경로(순환)의 거래 수 | 순환의 거래 전부 | ① + 이어지는 두 거래의 금액 비 0.8 ~ 1.25 |
| RANDOM | 경로의 끝 계좌 | 경로의 첫 거래 | 돌아오지 않은 경로의 거래 수 | 경로의 거래 전부 | 같음 |

- 자기 자신에게 보낸 거래는 룰이 보지 않는다
- 바쁜 계좌(72시간 안 같은 방향 거래 512건 초과, 필터를 걸기 전 거래로 센다)는 대상도 경유도 되지 않는다
- 경로형은 시간순(같은 분 포함), 같은 계좌를 두 번 지나지 않음, 첫 거래부터 마지막 거래까지 기간 안, 거래 12건까지
- 금액은 보낸 금액의 USD 환산(서비스 고정 환율)
- `첫거래` 필터를 켜면 쌍마다 거래가 하나만 남으므로 ④ 반복 없음은 저절로 만족된다

넣어 봤지만 뺀 조건 (HI-Small 보정 구간, 2026-11-23)
- **기간 안 금액 합계 ≥ 최소 합계** (Oracle 의 `Total_Trxn_Amt >= Min_Total_Amt` 꼴): 건당 최소 금액을 건 뒤에는 더해도 달라지지 않았다. FAN-OUT 의 F1 이 합계 0 / 1만 / 3만 USD 에서 0.558 / 0.558 / 0.560, 10만부터는 떨어진다
- **타행 거래만 · 통화가 바뀐 거래만**: 정상 거래의 84% 가 타행, 패턴 세탁은 96 ~ 99% 라 가르는 힘이 약하다. 통화가 바뀐 거래는 정상의 1.4%, 세탁은 0건이다

룰엔진 설계안(v3)과 다르게 둔 것
- CYCLE: 설계안은 최대 길이 5 와 최소 금액이 필수다. 여기서는 금액 비 조건을 필수로 두고 12건까지 따라간다. HI-Small 의 순환 시도 54개 중 21개가 6건 이상이라 5에서 끊으면 통째로 놓친다. 금액 비 조건이 있으면 경로 수가 적어 12건까지 가도 몇 초 안에 끝난다
- CYCLE 의 조건값은 최대 길이가 아니라 **최소 길이**다. 오탐이 2건짜리 순환(왕복)에 몰려 있어서다
- RANDOM: 단계 사이 간격 조건을 따로 두지 않고 기간 하나로 본다
- 첫 거래 후 경과 일수, 해외 송금 같은 덧붙이는 조건은 쓰지 않았다
- 바쁜 계좌 판정은 설계안 3.6 을 단순하게 옮겼다

### 조건을 고르는 방법
조건은 미리 정하지 않는다. 룰 × 필터 × 반복 × 기간 × 조건값 후보(1,065 벌)를 전부 돌려 **보정 구간**에서 룰마다 F1(정밀도 = 고른 거래 중 세탁 비율, 재현율 = 그 룰이 노리는 패턴의 세탁 거래 중 고른 비율)이 가장 큰 한 벌을 고르고, **평가 구간**에서 잰다. 모델이 검증 구간에서 의심 기준을 고르는 것과 같은 순서다.
비교용으로 "조건값 하나"(필터 없음, 반복 허용) 중 가장 좋은 것도 같이 낸다.

| | HI-Small | HI-Large |
|---|---|---|
| 보정 구간 | 09-01 ~ 09-08 | 10-03 ~ 10-16 |
| 평가 구간(= 모델 테스트 구간) | 09-09 ~ 09-10 | 10-17 ~ 10-30 |

### HI-Small 로 돌려 본 결과 (룰만, 2026-11-23)
보정 구간에서 고른 조건을 평가 구간(09-09 ~ 09-10)에 건 값이다. 정밀도 / 재현율(자기 패턴). 무패턴 · STACK · BIPARTITE 를 지표에서 뺀 기준이다.

| 룰 | 조건값 하나 | AND 로 묶음 | 고른 조건 |
|---|---|---|---|
| FAN-OUT | 0.7% / 18% (1,736건) | 96% / 37% (84건) | 1천↑, 반복 없음, 3일, 6개 이상 |
| FAN-IN | 0.3% / 14% (12,897건) | 4.1% / 30% (1,303건) | 첫거래+5천↑, 7일, 6개 이상 |
| GATHER-SCATTER | 65% / 16% (31건) | 100% / 24% (32건) | 첫거래+1천↑, 7일, 5개 이상 |
| SCATTER-GATHER | 84% / 28% (37건) | 86% / 45% (65건) | 1천↑, 7일, 3개 이상 |
| CYCLE | 90% / 31% (20건) | 같음 | 필터 없음, 7일, 3건 이상 |
| RANDOM | 75% / 35% (36건) | 같음 (36건) | 1천↑, 3일, 6건 이상 |
| 6종 합집합 | 0.8% / 26% (14,714건) | 15% / 48% (1,493건) | |
| FAN-IN 뺀 5종 | | 89% / 40% (207건) | |

합집합의 재현율은 지표에 남은 세탁(6종 패턴) 전부가 분모다. 보정 구간의 AND 합집합은 20% / 73% (5,317건)이다.
- FAN-OUT 과 GATHER-SCATTER 는 AND 로 정상 계좌가 거의 다 빠진다. 경로형(CYCLE·RANDOM)은 금액 비 조건이 이미 있어서 필터를 더해도 거의 같다
- **FAN-IN 은 여전히 약하다.** 평가 구간 정상 오탐 1,272건 중 1,249건이 FAN-IN 이다. 새 송금 계좌 여럿에게서 5천 USD 이상을 받는 정상 계좌가 많고, 송금 계좌 수가 많을수록 오히려 정상이다(조건값을 올리면 정밀도가 내려간다). 상한 조건이나 계좌 성격 조건이 더 있어야 한다
- **평가 재현율이 낮은 것은 대부분 구간 탓이다.** 평가 구간 6종 세탁 457건 중 334건이 09-10 뒤로 이어지는 시도에 속한다. 자기 룰 재현율이 구간 안에 끝난 시도는 67%(82/123), 이어지는 시도는 21%(71/334)다
- **작은 패턴은 끝까지 봐도 못 잡는다.** 보정 구간에서 시도 크기별 자기 룰 재현율이 3건 이하 15%, 4 ~ 5건 35%, 6 ~ 9건 60%, 10건 이상 77%다. CYCLE 을 뺀 다섯 룰은 5건 이하 시도를 하나도 못 잡는다(조건값이 5 ~ 6개 이상으로 골라져서)
- 보정 구간에서 자기 룰이 놓친 481건 중 337건이 조건값 미달 같은 모양 문제, 144건이 거래 필터에 걸러진 것이다. 바쁜 계좌 제외로 놓친 6종 세탁은 없다

### HI-Large 로 돌릴 때 (2026-11-23 준비. 아직 한 번도 안 돌렸다)
노트북 0절에서 `DATASET = 'HI-Large'` 로 바꾸면 아래 값이 같이 바뀐다.

| 설정 | HI-Small | HI-Large | 이유 |
|---|---|---|---|
| 기간 후보 | 1 · 3 · 7일 | 7 · 14 · 30일 | HI-Large 는 패턴이 길다. 시도 하나의 길이 중앙값이 FAN-IN · FAN-OUT · CYCLE 29일, RANDOM 21일, SCATTER-GATHER 32일, GATHER-SCATTER 56일(`docs/eda/large_eda.md` 3.1). 값은 설계안의 기간 목록에서 골랐다 |
| 경로형 기간 | 전부 | 14일까지 | 설계안 4.4.3 의 상한. 기간이 길면 경로 수가 폭발한다 |
| 앞으로 더 읽는 날 | 14일 | 30일 | 가장 긴 기간만큼. 읽는 범위가 09-03 ~ 10-30, 약 1억 건이 된다 |
| 룰 표를 두는 곳 | 메모리 | 파일(`parquets/HI-Large/rule_engine_work.duckdb`) | 메모리에 안 들어간다. `.gitignore` 의 `*.duckdb` 에 걸려 커밋되지 않는다 |

큰 데이터용으로 넣은 장치
- `REUSE = True`: 이미 만든 룰 표는 건너뛴다. 중간에 끊긴 실행을 이어 돌릴 때만 쓴다
- `MAX_WALKS`: 경로 수 상한이 이 값을 넘는 (필터, 기간)은 경로형을 건너뛴다
- 건너뛰었거나 만들지 않은 (룰, 필터, 기간)은 조건 후보에서 빠지고, 남은 것 중에서 고른다. 그래서 `FILTERS` 에서 큰 필터(`없음`, `1천↑`)를 빼고 먼저 돌려 볼 수 있다

돌리기 전에 알고 있는 것
- **소요 시간과 메모리를 모른다.** HI-Small(449만 건)이 3분이었고 읽는 거래가 20배를 넘는다. 기간이 길어져 거래당 계산도 늘어난다
- **폭발할 수 있는 곳**: SCATTER-GATHER 후보 추리기(경유 계좌마다 보낸 계좌 수 × 받은 계좌 수만큼 쌍이 생긴다), 이어지는 거래 쌍 만들기(계좌마다 입금 수 × 출금 수). HI-Small 에서는 둘 다 1초 안팎이었다
- **평가 구간 안에서 시도가 작게 보인다.** 02 실험 결과(`results/HI-Large/grouping_vs_truth`)에서 평가 구간 14일 안에 든 거래 수로 본 시도 3,242개 중 2건이 1,017개, 3 ~ 5건이 1,552개다(79%). HI-Small 보정 구간에서 자기 룰 재현율은 3건 이하 시도 15%, 4 ~ 5건 시도 35% 였다
- **CYCLE 은 대부분 닫힌 모양을 못 본다.** 시도 길이 중앙값이 29일인데 경로형 기간이 14일까지다
- **GATHER-SCATTER 는 30일로도 전부 안 보인다**(중앙값 56일, 최대 70일)
- 모델 쪽 비교 대상: 실험 1 이 HI-Large 에서 쓴 점수는 `gnn_structure/rev_port_test_scores.parquet`(의심 기준 0.556)이다

### 내는 표
1. 룰 × 필터 × 반복 × 기간 × 조건값: 대상 계좌, 고른 거래, 정밀도, 재현율 (보정·평가)
2. 고른 조건의 룰별 결과("조건값 하나"와 나란히), 룰 × 패턴 표, 룰 하나를 뺀 합집합
3. 룰 6종 합집합 vs 이진분류만: 거래 단위, 패턴별 재현율, 같은 건수에서의 비교, 세탁 거래를 누가 잡았나, 시도 단위
4. `hits.parquet`: 고른 거래 목록. 실험 3(룰 씨앗을 생성기에 넣기)의 입력. 지표에서 뺀 거래도 들어 있고 `skip` 열로 구분한다

### 03 의 한계
- **룰은 패턴이 완성된 뒤에야 걸린다.** HI-Small 평가 구간은 데이터의 마지막 이틀이라 걸친 시도의 절반 이상이 구간 뒤로 이어진다. 룰의 평가 구간 재현율은 그만큼 낮게 나온다. HI-Large 에서는 `LOOKAHEAD_DAYS` 로 뒤 거래를 보게 할 수 있다
- **HI-Small 평가 구간은 표본이 작다.** 패턴마다 세탁 거래 43 ~ 127건, 시도 17 ~ 37개다
- **`첫거래` 필터는 데이터가 시작한 직후에 약하다.** 앞 이력이 없어 모든 쌍이 첫 거래로 보인다. HI-Small 정상 거래의 첫 거래 비율이 09-01 51%, 09-02 24%, 09-05 이후 3 ~ 9% 다. 보정 구간 앞쪽이 이 영향을 받는다. 서비스에서는 "최근 N일 안에 거래한 적 없는 상대" 처럼 돌아보는 길이를 정해야 한다
- **`첫거래` · `반복 없음` 은 합성 데이터의 성질일 수 있다.** IBM 생성기가 세탁 패턴을 서로 거래한 적 없는 계좌들로 만들기 때문에 잘 듣는다. 실제 원장에서 같은 크기로 들을지는 모른다
- **후보가 많아져서 고르는 과정의 낙관이 커진다.** 룰마다 105 ~ 300 벌 중 하나를 보정 구간에서 고른다. 평가 구간 값을 따로 보는 이유다
- **기간 값은 데이터셋에 맞춰진다.** 합성 패턴의 길이는 데이터셋 길이에 비례한다(HI-Small 은 FAN·CYCLE 시도가 최대 96시간, 생성기 코드 주석 기준 HI-Large 는 840시간). HI-Small 에서 고른 기간을 HI-Large 에 그대로 쓸 수 없다
- 금액 비 0.8 ~ 1.25 는 생성기 정책에서 가져온 값이고, HI-Small 패턴 파일 전체에서 CYCLE·RANDOM 의 98% 가 이 범위인 것을 확인했다. 보정 구간만으로 고른 값은 아니다
- 검증 범위: 룰 SQL 은 HI-Small 에서 같은 정의를 Python 반복문으로 짠 계산과 일치했다(필터를 건 FAN 과 반복 없음 포함). 모델 쪽 셀은 가짜 점수 파일로 끝까지 도는 것만 확인했다. HI-Large 용 장치(파일 DB, 긴 기간, 건너뛰기, 이어 돌리기)는 HI-Small 데이터에 걸어서 도는 것만 확인했다. HI-Large 자체는 안 돌려 봤다(2026-11-23)

## 알고 있는 한계
- **실행 방식이 서비스와 다르다.** 서비스는 매일 이어서 돌고 공개된 Alert 를 고정한다. 여기서는 평가 구간 씨앗을 한 번에 넣고 한 번 돌린다
- **평가 구간 앞에서 시작된 패턴은 손해를 본다.** 앞 구간 거래에는 모델 점수가 없어 씨앗이 못 되고, 짝을 잃은 씨앗은 구조 없음으로 탈락한다. ③의 재현율이 낮게 나오는 방향이다
- **HI-Large 소요 시간과 메모리를 모른다.** 약 5천만 건을 순수 Python 색인으로 올린다. 탐색 예산 초과가 나면 `BUDGET_SCALE` 을 올린다
- **검증 범위**: 가짜 거래 3,000건으로 노트북이 끝까지 도는 것만 확인했다(2026-11-21)
