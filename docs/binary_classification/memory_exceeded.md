## binary_classification/01 — 메모리 초과 해결 기록 (서버 한도 약 25GB, HI-Large 양방향 3.4억 간선)

### 1차 사망 — 그래프 3개를 따로 생성
- 학습·검증·테스트 그래프를 각각 `torch.cat` 으로 통째로 생성. 그 시점에 tx(7GB)·basic_z(2.9GB)·트리 학습 배열까지 살아 있었음
- 학습 그래프 하나 만드는 중에 임시 복사본까지 20GB+ 추가 → 커널 사망
- 조치: 전체 간선 텐서 1벌만 만들고 학습·검증·테스트는 앞부분 슬라이스(뷰)로. 엣지 피처 float16, 라벨 uint8. tx·basic_z·X_train 은 쓰고 바로 삭제
  → 그래프 텐서 9.1GB, RSS 14.3GB

### 2차 사망 — 샘플러의 정렬 사본
- `LinkNeighborLoader` 의 샘플러가 그래프마다 간선을 도착 노드순으로 **정렬한 사본**(perm + row, 간선당 16바이트)을 만듦
  학습 2.3억 간선 3.7GB(정렬 중 순간 7.5GB) + 검증 2.8억 4.5GB(순간 9GB) → 사망
- 부수: `NUM_WORKERS=4` 면 이 사본을 /dev/shm 에 올리는데 Docker 기본 64MB 라 실패 → `NUM_WORKERS=0`
- 조치: 그래프를 만들 때 **미리 도착 노드순으로 정렬**해 저장하고 loader 에 `is_sorted=True` → 샘플러가 사본을 안 만듦.
  대신 앞부분 뷰 방식은 못 쓰므로 그래프마다 정렬본을 따로 생성 (빈 텐서를 미리 할당하고 제자리에서 채워 `torch.cat`·`stack` 복사본 제거)
  → 학습 13.3 → 검증 21.0 → loader 24.4GB

### 3차 사망 — 여유 0
- 그래프·loader 까지는 올라갔지만 첫 배치 샘플링에서 사망. 24.4GB 면 샘플링할 몇백 MB 여유도 없었던 것
- 조치: **그래프를 한 번에 하나만** 올림 (`use_graph('train'|'val'|'test')`)
  - 학습 중엔 학습 그래프만. 검증할 때 학습 그래프를 지우고 검증 그래프를 만들어 평가한 뒤 다시 학습 그래프를 만듦 (각 1분)
  - 그래서 검증은 `EVAL_PERIOD=2` 에폭마다, 테스트 그래프는 학습이 다 끝난 뒤
  - 셔플이 교체 때마다 새로 되지만, 30에폭이 전체의 14% 라 어차피 무작위 부분집합 → 결과 영향 없음
  → 학습 중 약 13GB, 검증 그래프 교체 순간 약 15GB (예상)

### 적용 중인 규칙
- 엣지 피처 float16, 라벨 uint8 로 저장. 배치에서만 float32 / long
- 큰 객체(tx, basic_z, 트리 배열)는 쓰고 바로 삭제 + `malloc_trim` (pandas 가 해제한 메모리를 OS 에 돌려줌)
- loader 를 전역 변수에 따로 담으면 그래프가 안 지워짐 → 항상 `use_graph()` 로 받아 바로 쓴다
- 각 단계에서 `trim()` 이 RSS 를 출력하므로 숫자로 확인
